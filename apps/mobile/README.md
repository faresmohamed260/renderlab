# RenderLab Android — Phase M0 development scaffold

**Status:** the M0 nonproduction scaffold is unmerged and not release-qualified; draft #403 has **emulator-verified** standalone Android navigation but has **not** been installed or validated on the owner's physical phone. Governing contract: `docs/architecture/MOBILE_APP_PHASE_M0_CONTRACT.md` and repository `AGENTS.md`.

## Architecture

Independent Expo SDK 58 / React Native / TypeScript / Expo Router app in `apps/mobile`. Four native tabs — Create, Library, Activity and Settings — are **placeholder scaffolds**, not product-complete features. Local gluestack-ui v5 (UniWind) Button and provider are generated from the maintained CLI. Colors mirror `docs/ui/UI_SYSTEM.md`. TanStack Query is wired for future server-owned data; Zustand is strictly local UI state. The original M0 typed API boundary performed URL validation only. This stacked draft now additionally makes an anonymous production guest probe and polls a strictly validated public UI configuration; **native authentication and private media are not implemented**.

## Local development

Use Node 24 and the committed lockfile: `cd apps/mobile && npm ci`. Start Metro with `npm start` and work in an Expo-compatible development environment. Expo Fast Refresh updates JS/UI during development without rebuilding native binaries. Initial app installation is still required; native modules/permissions or runtime upgrades require another native build. A real device, Android development client, Expo/EAS account, OTA Update service, and credentials **have not been configured or validated**.

Run `npm run typecheck`, `npm test`, `npm run lint`, `npm run export:android`, and `npx expo-doctor` before requesting review. `npm audit --omit=dev --audit-level=high` remains fail-closed for high/critical findings. On committed draft #403 implementation code head `0b6e4099d576bbfb5ccedcfeef74927bb7fce217`, it passed with `node-forge` 1.4.2 and seven low-severity advisories; see Checkpoint 35. This is **not** approval to introduce production credentials or distribute a release. Expo JS export alone is not device-rendering proof; separate emulator evidence is recorded below.

## Security and provisioning limits

No live Supabase/R2/Modal access, shared infrastructure changes, Android package identifier, auth callback, real secrets, signing key, EAS owner/project/runtime ID, APK distribution or OTA publish is authorized. An `eas.json` development/preview **template** exists but is not a provisioned channel/project. Do not add a production profile or imply release readiness. `.env.example` is illustrative only; `EXPO_PUBLIC_*` values are public.

Native session storage, invitation and MFA flows, per-route bearer/Origin checks, signed-media header stripping, device rendering, OTA compatibility fingerprint and production signing require separate evidence and permissions. Follow the M0 acceptance checklist in the contract and stop after M0 for further direction.

## Draft live UI configuration on the existing RenderLab backend — PR #403

PR #403 is stacked on draft production-read PR #402; **this is not released and requires an installed compatible Android build**. It adds a strict public first-party `GET /api/mobile/ui-config` endpoint to the same Next.js RenderLab backend. The mobile app reads it anonymously via HTTPS and applies bounded changes to its brand text, existing-tab titles/icons and tab order every 45 seconds in the foreground and on app resume. Invalid/missing responses preserve the last accepted config or embedded default. No new server, database, Metro process, EAS account, service credentials or production resource is involved in developing this code.

To prepare an authorized configuration change, edit the versioned `DEFAULT_ANDROID_UI_CONFIG` in `src/lib/api/android-ui-config-contract.ts`, or set `RENDERLAB_ANDROID_UI_CONFIG_JSON` as a **server-only** environment value with the exact same schema, and increment `revision`. Never put arbitrary code, navigation routes, backend URLs, account/entitlement state or secrets in config. The optional environment value is not a mutable live store; **a separately authorized new backend deployment** is required for changed production values. A mobile APK rebuild is not needed for schema-v1 text/tab layout changes **once the compatible APK has been installed**. Changing React Native logic needs a separately signed OTA update or APK release.

Tests are in `tests/unit/android-ui-config.test.mjs` (server) and `apps/mobile/tests/runtime-ui-config.test.mjs` (mobile). See `docs/architecture/MOBILE_APP_M1_PRODUCTION_READ_CONTRACT.md` Checkpoint 31 for the exact limits. **Do not tell the owner the current SDK53 offline APK or any other existing APK can load this remote configuration.** Real RenderLab login, signed media, native signing, update distribution, security qualification and actual phone testing remain separately blocked. WANDA is not used.

`src/services/auth/native-supabase-client.ts` contains an **unmounted, dormant** Auth-only SDK factory. `native-auth-config.ts` pins the existing shared project's public Supabase hostname, rejects foreign/malformed origins, rejects secret/service-role and malformed public keys, and hard-disables Auth at compile time. It does **not** include a real publishable key, connect a real user, send a bearer, expose the Supabase Data API to app screens, or perform a production request. The four native tabs, production guest probe and public UI-config mechanism remain unchanged.

`native-supabase-storage.ts` is an injected encrypted-`expo-secure-store` asynchronous adapter for larger Supabase Auth JSON, with bounded 1,800-byte UTF-8 chunks (maximum 32), a validated manifest, a pre-write/pre-delete tombstone, read-back verification and serialized refresh/logout operations. It deliberately rejects storage errors; no AsyncStorage or plaintext fallback exists. `native-auth-lifecycle.ts` is an injected AppState coordinator that starts auto-refresh only in the foreground, stops in the background, invalidates local admission on every suspend/resume and fails closed on refresh errors. At that earlier checkpoint these components were **not** mounted; current Settings now mounts the **disabled** Auth glue, with network Auth still hard-gated.

The prior AOSP 35 proof run [40628610677](https://github.com/faresmohamed260/renderlab/actions/runs/40628610677) verified the earlier *single-value* SecureStore boundary and a single local HTTP 302 refusal; it did **not** exercise this new multi-chunk Supabase storage adapter, SDK sign-in, real sessions, HTTPS redirects or other Android versions. All require further isolated emulator/device and Security/Architecture review before enabling native Auth. Do not treat successful unit/build tests as account admission, production readiness, OTA approval or phone installation.
