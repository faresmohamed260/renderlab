## Proposed hardening PRs — not implemented

1. **Status-conditional job updates / terminal immutability.** Require owner+job+expected state and reconciliation-token compare-and-swap for every terminal writer, with fault/replay/cancellation race fixtures, alerting on benign lost CAS. **Risk: medium–high** (an overly strict guard could reject an allowed in-flight transition or expose an existing race). Application runtime change: separate PR, exact-head CI and CodeQL, Vercel Deployment Readiness and rollback anchor, reviewed production deploy, same-sitting production-record PR and passing Production Documentation Sync; no Modal change unless independently proved necessary.
2. **Atomic terminalize-and-release.** Audit and add a transactional Postgres RPC that finalizes terminal job state, preserves one indexed output, binds/releases admission exactly once and refuses owner/claim mismatches. Validate concurrency and migration compatibility against disposable Postgres/Supabase, then stage reversible schema/app sequencing. **Risk: high** (schema privilege/security-definer behavior, transaction compatibility and rollout ordering). Requires explicit architecture/security/production approvals, migration and rollback plan, exact-head gates, qualified release and same-sitting production manifest/sync. No direct production SQL or Modal mutation in P0-05.

**Decision requested after merge:** Accept P0 test evidence while keeping the score target open, review the two hardening designs and P1 dependency ordering, and explicitly decide whether P0 closes with unmet gates or stays open. Neither a CI green check nor this proposal authorizes P1, production changes, or frontend.
