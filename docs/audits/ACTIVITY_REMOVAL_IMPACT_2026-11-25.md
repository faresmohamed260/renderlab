# Activity removal — impact analysis (2026-11-25)

**Status:** historical audit / proposal for Phase 6 contract review, not an implementation authorization. Worker 3, source-only, connector-driven.
**Baseline:** protected-main snapshot [`20062c84b017f7dac1835af4a7843bf7b622fe62`](https://github.com/faresmohamed260/renderlab/tree/20062c84b017f7dac1835af4a7843bf7b622fe62). Owner direction read separately in [approved comps README](https://github.com/faresmohamed260/renderlab/blob/claude/renderlab-adr005-handoff-zsbdq7/design/approved/2026-11-25-phase6/README.md): remove Activity destination; preserve its useful behavior in History and Queue. The comps are static, and their own README explicitly defers replacement edge cases and motion. They are not evidence of a working replacement. This audit does not change current decision authorities, runtime, API, data, provider, deployment or scope.

## 1. Executive finding

**Remove the screen, not the job ledger or lifecycle.** Activity is an account-wide, paginated server projection of durable jobs, with action eligibility, media-deletion rules and a distinct owner-return recovery trigger. The current Create Queue is workspace-local UI, not an account-wide job ledger. The existing session/result history is likewise not a substitute for the durable ledger. A successful job's recipe and Library asset do not replace failed/cancelled/in-flight jobs, which may have no asset. Sources: `src/app/(app)/activity/page.tsx`, `src/server/generation/generation-activity.ts`, `src/features/create/create-preview-workspace.tsx`, `src/server/generation/owner-generation-settlement.ts`, `src/server/generation/generation-recipe.ts`.

**Release blocker:** Activity is currently the only owner-settlement source selecting `includeActivityRecovery: true`; deleting that path would strand some cancellation/stale-dispatch recovery cases even if Create and Library still reconcile ordinary jobs. Preserve its bounded behavior in the History data boundary before removing the screen. No schema migration or new scheduler is needed for the proposed UI relocation.

## 3. Capability disposition (proposal)

History should have an account-wide **Jobs** segment (bounded server pages), separate **This session** results and **Prompt history**; these are distinct from Library. Desktop panel/mobile sheet are two presentations of the same contract. Queue is a compact current-work view, not a second lifecycle owner. A History entry from Queue opens the corresponding job in Jobs; use stable IDs, not row index.

### Critical recovery equivalence

`owner-generation-settlement.ts` distinguishes `create` (scheduled after response), `library` (bounded response settlement), `activity` (bounded response settlement with extra recovery) and `submit` (active bound job IDs). `reconcile-generation.ts:findOwnerSettlementCandidate` selects one owner candidate in last_reconciled_at/updated_at/id order. Activity recovery includes cancelling plus stale (>15 minutes) missing/non-FIBO dispatch cases in addition to normal persisting, bound-provider and expired FIBO candidates. Keep this exact extra predicate for History (e.g. retain source alias initially, or introduce explicit history source with equivalent recovery and update diagnostics/tests). Use bounded response wait/after-response continuation, existing claims and terminal guards. Poll only while appropriate and stop on closure/unmount/terminal/switch; preserve fair selection and no cross-account work. Current hasActive is page-local, so an older-page view can miss active jobs elsewhere; a new globally accurate active count would require a separately bounded owner projection, not guess from the first page. The owner-return policy for absent owners remains unchanged.

## Decisions taken 2026-11-25

Head engineer accepted the recommended defaults for the Phase 6 replacement. These answers supersede the open alternatives in sections 4 and 8; implementation remains gated on worker 2's P6-03 contract merge.
