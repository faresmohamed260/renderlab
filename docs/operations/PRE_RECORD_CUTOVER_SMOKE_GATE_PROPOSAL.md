# Pre-record cutover smoke gate — proposal

**Owner decision (2026-11-24):** Replace the hardcoded historical SHA gate; use the existing exclusive release window as the required operational race-control precondition. No stronger deployment-identity guard in this change.  
**State:** Reviewed design proposal; not an implemented policy, release/spend authorization, or current production record. Docs PR may open only after #694 merges. Implementation must be a separate PR and must not merge until Batch G release closure is confirmed.  
**Source review:** `edcd3b33d012509a31616b0530a3f91a7d12980a`, 2026-11-24.  
**Scope:** Production FIBO Smoke's optional pre-record cutover path, not routine recorded-release smoke, provider routing, application capabilities, migration or deployment policy.

## 1. Defect and evidence

[Production FIBO Smoke](../../.github/workflows/production-fibo-smoke.yml) is manual-only, requires explicit bounded fixture-provider-work confirmation and `expected_production_sha`, and runs only on protected `main`. Supplying `cutover_deployment_id` selects [the cutover wrapper](../../scripts/verify-modal-cutover-smoke-release.mjs); leaving it blank selects documentation sync plus normal live-state verification. The wrapper calls `verifyModalCutoverSmokeRelease` in [production-live-state.mjs](../../scripts/lib/production-live-state.mjs).

That function rejects every SHA except `c3f92247b21b9761fde6cee610cce2c9084441f8` and `e93481466806b3a88f986cd547f11ef62e9543fb`. Those were specific historical Modal cutover sources, not a reusable authorization rule. Only after the allowlist does it check scenario, deployment ID, alias/project, production target, READY state and deployment SHA. It does not bind qualification, staging evidence or alias assignment time.

[Batch E evidence](../audits/BATCH_E_RELEASE_EVIDENCE_2026-11-24.md) records the consequence: qualified source `80194dfe654bd7c34660c4679a8c97542db94387` could not use pre-record smoke; the owner authorized record → Documentation Sync → one smoke → evidence append → final sync. [Smoke run 45369816612](https://github.com/faresmohamed260/renderlab/actions/runs/45369816612) passed with exactly one fixture generation and cleanup. This was an authorized sequencing workaround, not an authorization to accept arbitrary live SHAs or weaken any guard.

## 2. Proposed replacement

Use the existing explicit release-SHA input as a candidate identifier, not as permission. Keep the existing optional deployment-ID input and scenario choices. For pre-record mode, also require a staged-release receipt identifier and the operator's independently read-back alias assignment timestamp. Routine mode continues to require the canonical manifest, five mirrors and existing live-state verification; it must reject any partial pre-record input bundle rather than silently falling back.

### Candidate identity and independent staging evidence

A trusted staging receipt is a small immutable, secret-free record captured before promotion by the authorized release operator through a protected-main, read-only qualification/receipt step. This is a proposed new evidence mechanism, not something the repository currently provides. Prefer a GitHub Actions artifact from a named protected-main workflow/run and attempt, identified by artifact ID and verified digest. Do not accept a receipt URL, free-form JSON from dispatch input, screenshot alone, or self-asserted SHA/deployment pair as equivalent to staging evidence. No extra long-lived credential or new shared infrastructure. Reuse existing authenticated read APIs and verify that the producing workflow is the reviewed one, on this repository's protected main, with successful conclusion and exact candidate head. Retain evidence long enough for the release record and its audit links; expired or unavailable receipts fail closed.

The receipt schema should contain:
- full candidate SHA; exact Vercel team/project IDs, domain, staged deployment ID and immutable deployment URL; READY production target and clean source provenance; observation time;
- current pre-promotion alias deployment ID, source and assignment timestamp; rollback deployment ID/source (same known-good deployment for ordinary releases);
- six required check-run IDs and Deployment Readiness run ID/attempt, latest successful qualification completion time, and applicable separately approved qualification evidence;
- intended release scope (app-only or worker changes), approved Modal app/version/source pair and compatibility evidence where relevant, and the operator's release authorization reference (not a credential).

The receipt must be created while the previous alias remains assigned and after the staged candidate is READY and qualified. Provider metadata establishes what is staged; the receipt establishes the authorized sequence and immutable identity. Require the previous alias to agree with the accepted manifest unless an explicitly reviewed recovery procedure says otherwise; do not invent a general recovery bypass. The receipt may be prepared by an approved staging workflow or a dedicated read-only step; select the precise workflow/artifact plumbing during implementation review. An artifact proves workflow provenance, not human consent by itself. Existing owner release approval and one-generation authorization remain mandatory.

### Pre-record verification algorithm

1. Validate manual event, protected-main ref and immutable checkout identity, exact 40-hex release SHA, strict deployment-ID grammar, positive artifact/run IDs, canonical UTC alias timestamp, allowed scenario, explicit exclusive-window attestation and explicit one-generation confirmation. Do not execute the input as a ref, command or URL. For the ordinary pre-record path require the candidate SHA to equal the dispatched protected-main checkout SHA and the frozen main tip; do not accept arbitrary ancestors. A later docs-only main tip is handled by the normal recorded-release path. A distinct recovery exception requires owner review rather than an override boolean.
2. Read the immutable stage receipt and independently fetch GitHub qualification evidence from the fixed repository. Reuse the protected-check context list and validation in the existing live-state verifier, including exact run/check identity, approved workflow identity, app ID, successful completed conclusion, exact head and valid timestamps. Verify protected main still points to the candidate and readiness + required checks completed no later than the receipt and cutover. Retain any existing required CodeQL/release-specific checks and approved qualification gates; do not substitute a smoke result for them.
3. Fetch Vercel deployment, custom-domain alias, and rollback deployment using the fixed RenderLab team/project/domain and existing token. Require exact receipt/input/provider equality for deployment ID, Git SHA, READY, production target, project and immutable deployment URL. Require clean, unambiguous source provenance (reject missing, conflicting or dirty provenance); verify rollback READY, same project and exact expected source. Verify the alias ID, project and actual assignment timestamp match the requested deployment and cutover input, and are later than the pre-promotion receipt observation and qualification. Reject conflicting alias fields rather than selecting whichever matches. Compare the still-accepted manifest to the receipt's prior release; this check is against the previous accepted release, not a claim that the new candidate is already recorded.
4. For releases involving Modal, require the existing independently verified compatible renderer/gateway pair and approved release evidence; do not grant the smoke workflow Modal management permissions. Record app/version/source evidence and operator attestation; app-only changes retain the existing pair. A missing verification or partial publish stops the operation.
5. Return a minimal validated tuple (candidate SHA, deployment ID, domain, alias assignment timestamp, staged-receipt ID/digest, qualification IDs, rollback ID and worker evidence reference). It is not a reusable authorization token. Revalidate at the boundaries in section 4. Only then may the existing bounded fixture smoke run; no additional provider work is authorized. The full production record and Documentation Sync still follow in the same operator sitting.

Do not maintain a historical release-SHA allowlist, let the current manifest's old SHA block a qualified pre-record transition, or add a skip-verification switch. Historical cutovers remain auditable in the dated release evidence. Retain the normal recorded-release gate unchanged.

## 3. Security and authority

- Preserve [ADR-004](../architecture/ARCHITECTURE_DECISIONS.md) and [governance](../../GOVERNANCE.md): separate human merge, release and spend authorization; protected-main checkout only, manual dispatch, explicit confirmation, one disposable fixture generation. No PR, fork, schedule, reusable untrusted caller or arbitrary revision checkout for the privileged workflow. No change to required checks, branch protection, Vercel automatic-deploy policy, or permitted release authority.
- Preserve read-only GitHub contents/actions/checks and Vercel verification calls. The receipt producer must be protected-main and read-only toward providers; no new provider management scopes, tokens or credential-bearing artifacts. If artifact production requires additional GitHub permissions, scope them to that job and review separately. Use the existing exact fixture ownership/cleanup boundary for the only allowed shared-resource mutations.
- Use fixed HTTPS provider hosts, scoped project/team, bounded timeouts, strict schemas, encoded IDs, and no redirects carrying credentials outside the approved origin. Prefer sanitized error labels/statuses, not raw provider bodies (the current shared fetch helper includes a response-body excerpt; review this path before reuse). Do not log secrets, headers, raw credential-bearing responses, signed URLs, or environment values. Supply Vercel/GitHub read credentials only to gate steps and keep them out of browser/fixture subprocesses; minimize Supabase/R2 secret exposure to the authorized fixture/cleanup steps. Do not broaden the existing job-level secret scope.
- Missing/ambiguous/malformed/unavailable data, timeout, rate limit, revoked authorization, failed or stale check, wrong repository, wrong deployment, wrong alias, or incomplete receipt stops before fixture mutation. Bounded read-only retries may occur within the gate timeout; no mutation retry or fallback to a weaker path. A successful gate never substitutes for owner authorization.

## 4. Race and cancellation safety

### Release serialization and alias identity

The existing smoke concurrency group serializes smoke runs, not Vercel console/CLI promotions or Modal publication. A one-time alias check before dependency installation cannot prove the deployment serving a later POST.

**Enforced precondition (owner decision):** The existing single-releaser procedure, merge freeze and prohibition on concurrent promotions constitute the exclusive release window. The authorized operator must explicitly attest that the window is active for this exact candidate before dispatch; the protected workflow must reject absent/false attestation. Keep the freeze through staging, promotion, smoke, cleanup, record closure and final sync. All authorized promotion/rollback/worker-publish paths must honor the window; no competing promotion, rollback or worker publication except emergency risk containment. Record the operator, frozen candidate, window start and any handoff. This is an enforced operational precondition, not a claim that GitHub concurrency locks Vercel or Modal. No new lock service, API fence or deployment-identity guard. If the window cannot be established, stop the pre-record path and use the documented record-first procedure only after the operator confirms a safe release state.

Required read-back sequence:

1. **Immediately before workflow dispatch**, the single releaser independently reads the live custom-domain alias and the deployment it actually targets. Verify the full deployment Git SHA, deployment ID, project and alias assignment timestamp against the qualified staged release; do not dispatch on any mismatch, uncertainty or broken freeze. Include the observed identity and window attestation with the dispatch inputs/evidence. The workflow cannot itself perform a check before its own dispatch: this is the operator-side gate.
2. **Inside the workflow**, perform the full read-only gate before fixture mutation. After dependency/browser setup, repeat the live alias/deployment SHA verification immediately before the single generation step (after any pre-clean); compare the complete frozen identity, including alias assignment timestamp and main SHA. No generation if the read fails or differs. Do not pass Vercel credentials into the browser or generation subprocess. Keep the exclusive window active across the small interval between this final gate and submission.
3. After submission/settlement, independently read back the alias identity before accepting evidence. A changed deployment or an ABA reassignment (same ID, changed assignment timestamp) invalidates attribution; settle and clean the original fixture without automatic retry. Recheck approved worker evidence on handoff or suspected change.

The owner accepts the residual non-atomic check-to-POST gap under the exclusive release window. Repeated reads detect mismatches but do not physically prevent out-of-band promotions. No stronger deployment-identity check, pinned routing or application change is in scope. A window violation stops pre-record smoke; retain record-first sequencing as the documented fallback after safe reconciliation.

### Cancellation and at-most-one spend

Keep manual confirmation and `cancel-in-progress: false`; reject a second dispatch/re-run for the same approved spend unless the owner supplies fresh authorization. A failed/cancelled/ambiguous POST can have been accepted; a missing response or manifest count of zero is not proof that no GPU work occurred. Persist a durable, release/run-bound submit-intent marker before issuing the POST, bind the existing idempotency key where supported, count attempted/possibly accepted work conservatively, never resubmit automatically. An approved rerun of read-only checks or cleanup is not approval to regenerate. Propose a run/attempt-aware, exact fixture identity and independent evidence ledger or equivalent durable marker using the existing authorized repository/run/fixture mechanisms; implementation must demonstrate that a runner crash cannot erase the only record of possible spend. If no safe durable marker can be established, fail closed and require operator reconciliation before any new smoke.

Cancellation before fixture creation or submission: stop and record zero dispatched if independently established. After submission begins: stop new provider work, reconcile the exact fixture job/handle through the supported lifecycle and wait for terminal state and released reservation (bounded; no forced job deletion as a substitute for settlement). Never cancel or delete unrelated jobs. Track outbox/late writes and exact R2 keys, then run the existing owner-scoped cleanup and independent read-back. Retain finally cleanup and the separate unconditional cleanup step; cancellation or runner loss may prevent either from finishing. On cancellation, timeout, uncertain settlement or incomplete cleanup, record failure/unknown, keep release closure blocked and require separately authorized cleanup-only recovery for the exact original fixture. Do not widen cleanup to other owners. A new generation is not the recovery mechanism.

An emergency rollback during smoke stops the run, marks evidence invalid/possibly spent, preserves the original fixture identity, reconciles safely and invokes the documented authorized rollback procedure. No automatic deployment rollback or automatic promotion from smoke. The release operator must not release the freeze solely because a GitHub run ended.

## 7. Rollback and stop criteria

Reject activation or stop the release on any incorrect acceptance, false rejection of a correctly qualified receipt, loss of main-ref/secret boundary, stale alias attribution, ambiguous spend, unsafe cancellation or incomplete cleanup. Hold the operator window; establish fixture disposition and live alias/worker pair independently. Revert the gate implementation and docs together through protected main, or disable use of the optional cutover path and use the existing record-first procedure with explicit owner approval. Do not restore a permissive fallback or add a third historical SHA. Reverting CI code does not roll back a live deployment; if production risk requires it, the authorized operator uses the known-good rollback anchor and compatible Modal pair per runbook, then reconciles the production record and sync. No automatic rollback from the verifier. A failed post-dispatch gate is not a refund of the one-generation allowance.
