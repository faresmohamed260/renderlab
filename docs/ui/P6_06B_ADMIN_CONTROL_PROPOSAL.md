# P6-06B — Admin Control proposal

**PROPOSAL · Future intent · Not authorized.** The Observe contract authorizes a read-only presentation slice. Its later roadmap names User Control, Job Control, Audit Log and Guards. The order below is a recommendation for future owner review, with audit and guards considered prerequisites for exposing new mutations. Scope only the next approved slice after Observe review. [Observe scope and exclusions](P6_06_ADMIN_OBSERVE_CONTRACT.md#L20-L43), [Observe roadmap](P6_06_ADMIN_OBSERVE_CONTRACT.md#L54-L58), [progressive phase planning](../../AGENTS.md#progressive-phase-planning).

## Operator boundary

Today the server checks fresh verified authentication, an active RenderLab `admin` record, verified MFA enrollment and current AAL2. The page redirects eligible admins to enrollment or challenge and returns not-found on denial. The API independently enforces authorization and returns 403 on denial. The existing role model has `member` and `admin`. If a future control must be restricted to one designated owner among active admins, the owner must approve the server-side principal rule before any new control is exposed. Navigation visibility does not establish that authority. [Admin authorization](../../src/server/admin/admin-auth.ts#L27-L49), [page gate](../../src/app/%28app%29/admin/page.tsx#L51-L68), [API gate](../../src/app/api/admin/admin-api-authorization.ts#L8-L32), [role model](../architecture/PRODUCT_CAPABILITIES.md#L360-L365), [UI-088](UI_DECISIONS.md#L752-L757).

For every proposed mutation, require the approved actor scope, fresh admin authorization and AAL2 at the server entry point, plus the existing same-origin mutation guard. Require a reviewable record of actor, target, action, reason, allowed before/after fields and outcome. For job actions, distinguish a request accepted for cancellation from a terminal cancellation. A confirmation should identify the target and impact, require deliberate submit and be invalidated by a relevant state change. For destructive or broad-impact actions, review a separate server-enforced, action-bound re-authentication requirement. The current AAL2 check supplies session assurance. Existing settings and account routes perform the origin and actor checks before the update. [Settings route](../../src/app/api/admin/settings/route.ts#L37-L49), [account route](../../src/app/api/admin/accounts/%5BuserId%5D/route.ts#L50-L66), [cancellation outcomes](../../src/app/api/generation/jobs/%5BjobId%5D/cancel/route.ts#L37-L42), [Observe roadmap](P6_06_ADMIN_OBSERVE_CONTRACT.md#L54-L58).

## Recommended order

1. **Health, queue and capacity reads · Not authorized.** Build on the existing sanitized Health view if further presentation is approved. The loader already combines active job age, dispatch backlog/heartbeat, bounded reservations, admission defaults, diagnostics and alerts. Observe adds confirmation latency and unreleased terminal reservations with sampling and availability qualifiers. Keep the read under the operator gate above. No destructive confirmation or mutation audit event applies. Existing aggregates need no new read or migration. A job-level queue view would need a separately authorized server projection. [Health loader](../../src/server/admin/admin-operations.ts#L335-L397), [Health response](../../src/server/admin/admin-operations.ts#L426-L451), [Observe presentation rules](P6_06_ADMIN_OBSERVE_CONTRACT.md#L20-L29).
2. **Audit Log and Guards · Not authorized.** Establish accountability before exposing further writes. Global settings retain the last updater and timestamp, and Health exposes retained diagnostics and alerts. The account update persists the target fields and timestamp. A durable action ledger and action-bound confirmation or re-authentication would require explicitly owner-authorized backend work, plus owner authorization for any persistence migration. Restrict ledger reads to the approved operator scope with fresh admin authorization and AAL2. A ledger read needs no destructive confirmation. Review retention, failure handling and record integrity before choosing storage. [Settings update SQL](../../supabase/migrations/0012_renderlab_generation_admission.sql#L205-L240), [account update SQL](../../supabase/migrations/0011_renderlab_admin_access_control.sql#L97-L126), [diagnostics projection](../../src/server/admin/admin-operations.ts#L442-L451).
3. **User Control and admission limits · Not authorized.** Start with existing per-account overrides and global defaults. The current UI saves these through the Admin routes. The server permits 1–4 active jobs and 1–120 hourly admissions, and `null` on a per-account field restores its default. Existing account access writes can also change role or suspension and preserve self-lockout and last-active-admin protection. Review before/after values and scope before saving. Require destructive-action confirmation for suspension or demotion and explicit confirmation for broad-impact limit changes. Audit each target and effective change under the operator gate above. The existing fields need no new schema. A narrower owner rule, action confirmation enforcement and persistent audit are separately owner-authorized backend work. [Existing settings UI](../../src/features/admin/admin-operations.tsx#L670-L690), [account override UI](../../src/features/admin/admin-operations.tsx#L775-L797), [account validation](../../src/app/api/admin/accounts/%5BuserId%5D/route.ts#L14-L28), [default validation](../../src/server/admin/admin-settings.ts#L33-L57), [lockout protections](../../supabase/migrations/0011_renderlab_admin_access_control.sql#L97-L124).
4. **Pause or resume admissions · Not authorized.** The generation default and account override affect new admission. An explicit account override takes precedence over the default, so a default pause can leave some accounts enabled. The settings RPC edits defaults, and its write does not interrupt accepted jobs. Require explicit confirmation of scope and impact for pause or resume and audit the effective policy change. An override-proof pause or any pause affecting dispatch or accepted jobs would require separately owner-authorized backend policy and authorization for any RPC or schema migration. [Admission precedence and check](../../supabase/migrations/0012_renderlab_generation_admission.sql#L68-L93), [settings write](../../supabase/migrations/0012_renderlab_generation_admission.sql#L222-L240).
5. **Cancel one stuck job · Not authorized.** Current cancellation derives the job owner from the admitted caller. The service has a pre-dispatch branch and uses a reconciliation claim and eligibility rechecks for supported native cancellation. Age alone cannot establish eligibility. An operator cancelling another user's job needs a new, explicitly owner-authorized server action and minimal target lookup, with actor and job owner kept distinct. Require single-job destructive confirmation with reason, current eligibility recheck and audit of the request and outcome. Preserve dispatch claims, durable-output protection and reservation settlement. Require separate owner authorization for any lifecycle or RPC migration. Keep bulk cancellation and forced terminal states outside this candidate. [Owner API](../../src/app/api/generation/jobs/%5BjobId%5D/cancel/route.ts#L15-L42), [cancellation service](../../src/server/generation/cancel-generation.ts#L305-L387), [pre-dispatch SQL guard](../../supabase/migrations/20261120022122_modal_dispatch_recovery.sql#L191-L214).
6. **Spend readout · Not authorized.** Capacity and timing are available from Health. The Admin DTO has no spend or billing field. Actual spend requires an explicitly owner-authorized source, attribution rules and read-only backend integration before it can be shown. Require separate approval for any persistence migration. Keep the same fresh operator gate and restrict the projection to approved RenderLab aggregates. No destructive confirmation or mutation audit event applies to a read. [Health DTO](../../src/lib/api/admin-contract.ts#L65-L147), [product boundary](../architecture/PRODUCT_CAPABILITIES.md#L360-L369).

Any future authorized presentation should use dark Violet Studio glass, semantic tokens and existing shared primitives within Admin's 1/4 motion ceiling. Deployment and provider operations remain separate from web Admin, including secrets and credential management. [Observe material and scope](P6_06_ADMIN_OBSERVE_CONTRACT.md#L29-L35), [server-only credential boundary](../architecture/INFRASTRUCTURE.md#L323-L329), [governance decision boundaries](../../GOVERNANCE.md#L29-L53).
