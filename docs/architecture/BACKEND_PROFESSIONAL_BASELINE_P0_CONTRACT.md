Make RenderLab's already-operational closed-beta backend defensible to a skeptical AI Engineer hiring manager: truthful claims, validated production configuration, explicit security boundaries, a testable job state machine and deterministic recovery evidence. The owner gains a reliable personal/friends beta without surprise costs or configuration regressions; employers gain short, reproducible source and test evidence. This phase changes engineering confidence, **not** the product's live feature set.

This is Node-unit coverage only, not overall behavior/acceptance coverage. The live [production manifest](../production/current.json) records FIBO image create/edit/masks on application SHA e209bfee430c8e61789aeabc8a63579f05b0435c. Phase 1 and Phase 2 are closed; Phase 2 proved one admin alert email received, isolated cleanup, and the oldest-active-job signal. Browser-independent **dispatch** is live; completed jobs are settled **on owner return**, not unconditionally in the background. No scheduler for never-returning users is approved.

This is **Phase 3 of the present backend/product reliability cycle** (after Phase 1 beta correctness and Phase 2 operational reliability), not a restart of unrelated historical UI phase numbers. It **replaces proposed creative-productivity implementation** as the immediate next phase. New models, video, frontend redesign and new creative functionality remain planned but unapproved.

**Architecture/data/security implications:** No new database migrations or worker deployments are part of this contract. Document the anonymous → signed-in owner → admin/AAL2 → service-role → worker trust boundaries, threats (cross-owner reads/writes, stolen sessions, forged provider state, replayed dispatch, secret/log leakage), and controls/evidence. Use sanitized synthetic identifiers in tests. Never print secret values.

## P0-02 typed configuration guardrails

Separate **required** environment values from **optional** flags with explicit typed defaults. A missing optional feature flag must not break unrelated routes; a missing/invalid required value should fail fast only when the service or privileged operation can safely refuse startup/acceptance (e.g. eligible production build/gateway submission), rather than taking down an otherwise safe read-only or recovery path. Missing admission/enforcement controls must **fail closed** in production, not silently switch beta access off. Document each check's build/runtime/feature boundary, evaluation order and rollback. An optional disabled feature must not require credentials for its inactive provider.

**Names-only Production inventory (16 required names for current enabled product):** SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, SUPABASE_SERVICE_ROLE_KEY, CLOUDFLARE_R2_ACCOUNT_ID, CLOUDFLARE_R2_ACCESS_KEY_ID, CLOUDFLARE_R2_SECRET_ACCESS_KEY, CLOUDFLARE_R2_BUCKET, RESEND_API_KEY, CRON_SECRET, RENDERLAB_GENERATION_RECONCILER_SECRET; RENDERLAB_FIBO_GENERATION, RENDERLAB_GENERATION_GATEWAY_URL (or documented legacy alias RENDERLAB_FIBO_GATEWAY_URL), RENDERLAB_FIBO_MODAL_KEY, RENDERLAB_FIBO_MODAL_SECRET, RENDERLAB_CLOSED_BETA_ACCESS_ENFORCEMENT_ENABLED, RENDERLAB_FIBO_MASK_ENABLED. The first ten are baseline build-preflight names; the final six are currently enabled FIBO/admission policy names (the gateway URL has one accepted alias, not two simultaneous requirements). Record exact observed present/absent **names and boolean effective behavior only**, scoped to the correct Vercel team/project/Production environment; never store values or hashes of secrets. Compare with scripts/verify-vercel-env.mjs and the production release runbook, and explicitly stop on drift rather than fabricating presence. Include the closed-beta and mask flags in positive/negative preflight tests. Distinguish expected required production features from optional development defaults. The inventory is a **future P0-02 verification gate**, not a claim that it was re-verified by this contract PR.

**Rollback required for startup-affecting changes:** capture last READY production deployment/manifest, describe disabling the new guard only through a reviewed rollback commit or returning to the verified deployment (not weakening access controls), and verify both existing healthy routes and fail-closed private authorization. Do not promote a behavior change without separate owner authorization and the runbook.
