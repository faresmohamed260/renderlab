# History Jobs keyset cursor design note

**Advisory design · Implementation and cutover require separate approval.** Activity was the original reference for the owner-scoped Jobs projection; the replacement uses the same bounded History reader. At base `2fd33e7`, Activity resolves the current account, performs bounded owner settlement, and loads 20 rows per page using offset. The shared reader orders by `created_at DESC, id DESC`, fetches an extra row and filters deleted results after slicing the raw page. Prompt history already uses the same ordered keyset, with a prompt-specific operation filter and its own cursor. Keep the Jobs and Prompt history views independently scoped. [Activity route](../../src/server/generation/history/history-activity.ts), [Jobs projection](../../src/server/generation/generation-activity.ts#L82-L135), [Prompt history query and cursor](../../src/server/generation/history/prompt-history-model.ts#L29-L64).

## Seek by creation time and job ID

For Jobs, use the database's `(created_at, id)` pair, with both columns descending. The initial page has no boundary. An older page adds the strict predicate `created_at < T OR (created_at = T AND id < I)` under the same `owner_id = account.id` condition. Fetch 21 raw rows for 20 slots. Emit an older cursor using the last consumed raw row when there is a lookahead. Keep the lookahead for the next query. Derive the boundary before UI-067 output filtering, so a page of entirely hidden results can still advance. Preserve the current same-owner media lookup and action eligibility. The timestamp keeps its original microsecond precision and the UUID breaks ties in database order. [Jobs page and media lookup](../../src/server/generation/generation-activity.ts#L72-L135), [timestamp precedent](../../src/server/generation/history/prompt-history-model.ts#L12-L21), [P6-04 parity rules](../ui/P6_04_CREATE_CONTRACT.md#L25-L29).

For Newer from a direct link or after refresh, use the first consumed raw row as the boundary, apply the strict inverse comparison, read in ascending order and reverse the first 20 raw rows for presentation. Determine availability on the opposite side with a bounded one-row existence seek when needed. Both directions traverse the same raw relation and use the existing display filter. Keep Newest as an explicit reset if a bookmarked cursor returns no raw rows. Treat each read as a view of current data. A job newly inserted above an older boundary appears on Newest or when navigating newer, and deletion of the boundary row does not invalidate a comparison against its saved values. [Current newer and older controls](../../src/features/activity/activity-view.tsx#L325-L345).

## Cursor and owner boundary

Use a versioned URL-safe token for Jobs navigation. Proposed envelope is base64url-encoded JSON with exactly `v`, `direction`, `createdAt` and `id`, plus a base64url HMAC-SHA256 signature over the payload and a Jobs-purpose tag and current account ID. Keep the signing key server-side, with separate owner review for key configuration and rotation. The token carries an opaque job ID already present in the authorized projection and an ordering timestamp. Avoid logging or caching the token in shared contexts. Keep persisted bookmark readability in the key-rotation decision.

Resolve the current account through the existing server boundary. Before settlement or job queries, reject oversized tokens, malformed encoding, invalid signatures or wrong owner scope, unknown versions, unknown keys and directions, malformed UUIDs, and invalid calendar dates, time components or offsets. Preserve the exact timestamp string for the seek after validation, including fractional seconds. Use strict, allowlisted values and `URLSearchParams` if composing the PostgREST expression. Keep `owner_id` as a separate mandatory filter on every seek and existence probe. The token establishes a position only. On bad input offer a generic restart from Newest, with no membership or job existence signal. Clear paginated state and discard in-flight old-account responses on account switch or logout. [Account resolution](../../src/lib/supabase/server.ts#L160-L174), [owner-scoped prompt reader](../../src/server/generation/history/prompt-history.ts#L6-L14), [validated seek precedent](../../src/server/generation/history/prompt-history-model.ts#L29-L53), [P6-04 privacy boundary](../ui/P6_04_CREATE_CONTRACT.md#L35-L41).

## Index and query plan

- The checked-in index that matches the Jobs query is `generation_jobs_owner_created_at_idx` on `public.generation_jobs (owner_id, created_at DESC, id DESC)`. Reversing the scan supports the inverse order after equality on owner. The schema gives `id` a UUID primary key, declares `created_at` as non-null `timestamptz`, and later makes `owner_id` non-null. [Index definition](../../supabase/migrations/0004_core_account_ownership_prepare.sql#L13-L17), [job schema](../../supabase/migrations/0002_generation_jobs_media_assets.sql#L1-L26), [owner enforcement](../../supabase/migrations/0005_core_account_ownership_enforce.sql#L18-L31).
- The primary-key index can locate an individual ID. The status index `generation_jobs_status_created_at_idx` has neither owner nor ID as an index key. The provider-ID index is for provider lookups. The active reconciliation and fairness indexes are partial, ordered by lease or reconciliation/update timestamps, and lack the chronological key even in the owner-prefixed fairness index. They do not supply the owner-scoped Jobs ordering. [Job lookup indexes](../../supabase/migrations/0002_generation_jobs_media_assets.sql#L1-L32), [active reconciliation index](../../supabase/migrations/0016_generation_cancellation.sql#L14-L19), [fairness indexes](../../supabase/migrations/0033_generation_reconciliation_fairness.sql#L9-L15).
- Start with the existing index and the existing PostgREST access path. Test the actual predicate and query shape. PostgreSQL may apply the OR as a filter after scanning an owner range, which can retain deep-page cost. Compare the plan to a tuple seek `(created_at, id) < (T, I)` and its inverse, which express one lexicographic range. If serving an efficient tuple seek requires a new SQL RPC, it is a backend and migration proposal. A new or replacement index would also be a migration requiring explicit owner authorization. The checked-in index definition establishes suitability for the order and potential range scan. Planner behavior remains to be measured. [Existing PostgREST seek](../../src/server/generation/history/prompt-history-model.ts#L36-L52), [P6-04 migration boundary](../ui/P6_04_CREATE_CONTRACT.md#L31-L37), [database verification gate](../operations/DATABASE_CONFORMANCE_GATE.md).

## SEC-02 and legacy links

The owner-reviewed SEC-02 entry is recorded in commit `82db40ef83c4ca4f798c5c77d50b016e2580786b` on the held #740 lineage. It accepts the existing deep-offset availability cost for P6-04, forbids an arbitrary offset ceiling or weaker guards, and calls for a separate follow-up after the Activity successor is verified. The base contract keeps Activity until verified parity and specifies an owner-directed temporary same-origin 307, with valid older offsets carried to `/create?history=jobs&historyOffset=…`. The proposal depends on separate parity and cutover decisions. [SEC-02 and SEC-01 record](https://github.com/faresmohamed260/renderlab/blob/82db40ef83c4ca4f798c5c77d50b016e2580786b/docs/ui/P6_04_CREATE_CONTRACT.md#L43-L46), [base compatibility contract](../ui/P6_04_CREATE_CONTRACT.md#L25-L29), [accepted redirect defaults](../audits/ACTIVITY_REMOVAL_IMPACT_2026-11-25.md#L129-L138).

After parity and with cutover approval, generate cursor links for ordinary Jobs traversal and keep a legacy offset entry for bookmarks. Have the redirect forward only the reviewed legacy parameter to the same-origin History destination, normalize malformed or negative values, and do no private work in the redirect. At the authenticated destination, resolve the initial legacy page with the exact existing offset projection, then derive neighbors from the raw first and last rows. Preserve the legacy URL for refresh and back/forward. For out-of-range legacy offsets keep a route to newer positions or Newest, with an honest empty state. Define cursor and legacy offset as mutually exclusive inputs. Legacy requests retain their accepted scan cost whenever revisited, and should still do at most the existing bounded settlement per read. Retiring that compatibility path requires a later owner decision with navigation evidence. Keep recipe, source and action links compatible. [Legacy offset parser](../../src/features/create/history/history-entry.ts) and [History reader](../../src/server/generation/history/history-activity.ts), [current empty-page navigation](../../src/features/activity/activity-view.tsx#L267-L291), [settlement boundary](../../src/server/generation/owner-generation-settlement.ts#L21-L39), [Create compatibility acceptance](../ui/P6_04_CREATE_CONTRACT.md#L48-L53).
