# P0-03 — Trust boundaries and owner isolation

**Status:** Owner-approved security architecture contract, docs-only merge gate. **Phase:** Backend professional baseline (P0), Unit 3. **Date:** 2026-11-23. **Owner:** Engineering / security review. **Authorization:** Owner approved the threat/access matrices with a static call-site registry and sequential 3a sanitization before 3b isolation; **no test or runtime change is implemented by this document**.

## Goal, verified baseline and non-goals

An invited member must be able to operate only on their own jobs, media, references, collections, uploads, account data and generation reservations. Admin operations require a freshly verified active admin identity and AAL2. Internal maintenance and worker reconciliation must not be reachable merely by sending a user-controlled identifier. A reviewer must be able to trace these rules from an API boundary to the service-role query and to a negative fixture.

Production P0-02 documentation sync [#45182864076](https://github.com/faresmohamed260/renderlab/actions/runs/45182864076) succeeded for application SHA 30634662fb0319e3b6a943af2c89872ef607104b; release manifest is [current.json](../production/current.json). Current FIBO-only and invite-only scope remains unchanged. The live [service-role REST wrapper](../../src/server/data/supabase-rest.ts) forwards a server credential to PostgREST; **service_role bypasses RLS**, so caller-supplied owner IDs or an RLS assumption cannot protect these operations. [Fresh session validation](../../src/lib/supabase/server.ts), [closed-beta access lookup](../../src/server/account/account-access.ts) and [admin AAL2 authorization](../../src/server/admin/admin-auth.ts) are independent gates.

**Out of scope until a separate reviewed follow-on:** schema/RLS migrations, changing auth providers, new routes or public API contracts, browser UI work, provider and Modal changes, generations, secrets, S.A.G.A. or resume work. This first PR is **docs only**; adversarial tests and runtime sanitization are expressly deferred until the owner reviews this matrix.

## Trust boundaries and principal matrix

| Principal and entry boundary | Trusted proof | Database authority / RLS | Permitted operations | Must never be trusted for |
| --- | --- | --- | --- | --- |
| Anonymous browser | None | Public pages and intentionally public health/capability reads only | Landing, safe health and GET generation capabilities | Private asset/job/account IDs or privilege escalation |
| Signed-in active member | Supabase getUser + getClaims, matching session_id, live Auth session, valid MFA state, active invitation/admission | User JWT may be subject to grants/RLS; privileged server operations use separately authorized service-role calls | Own Create, Activity, media, uploads, collections and account workflows | Arbitrary owner_id/user_id supplied in JSON, URL, headers, or query |
| Signed-in suspended, uninvited, revoked or stale session | Authentication may exist but effective access is absent | No private RenderLab access | Generic denial / no private data | A still-valid JWT as proof of active membership |
| Active admin with verified MFA/AAL2 | Fresh authentication plus current active admin role, verified factor, currentLevel=aal2 | Server-only service-role operations under explicit admin gate | Admin accounts, invitations, settings and bounded health | AAL1 session, user metadata role claim or forged admin header |
| Server service-role REST/Auth client | Server-only SUPABASE_SERVICE_ROLE_KEY, never exported to browser | Bypasses RLS / can use privileged Auth admin methods | Only the operation already authorized for the verified owner or qualified internal/admin principal | Implicit ownership from service_role capability or arbitrary DB rows |
| Internal maintenance/reconciliation | Distinct server bearer secret (GET cron vs POST maintenance; reconciliation internal secret) | Privileged bounded server work | Allowed maintenance/recovery paths only | A browser user JWT, untrusted owner header or caller-selected global sweep |
| Storage / provider capability | Short-lived R2 URL or private Modal gateway credentials obtained server-side | Neither proves RenderLab account ownership | Read/write only the already approved object or provider handle | Authorizing an asset by knowing its key, URL, job ID or provider call ID |

**Key boundary:** derive effective owner ID from server-verified authentication, not URL or request JSON. An admin's ability to inspect another account is **an explicit audited admin operation**, not permission for ordinary user routes to ignore owner filtering. Source: [server authentication](../../src/lib/supabase/server.ts), [admin API guard](../../src/app/api/admin/admin-api-authorization.ts), [service-role REST](../../src/server/data/supabase-rest.ts), [maintenance secret gates](../../src/app/api/internal/maintenance/route.ts).

## Compact threat model

| Threat / attack entry | Protected asset / expected denial | Existing boundary and residual verification gap | Required negative proof ID |
| --- | --- | --- | --- |
| Predict another member's UUID and read/change/delete it | Generation jobs, media, collections and owner-bound storage URLs must look absent to outsider | Many server queries explicitly filter owner_id; enumerate **every** service-role filter, not only a successful route | O1–O5 |
| Inject foreign owner ID into body, query, header or RPC argument | No cross-owner mutation, reservation, export or generated result | API owner is expected from session; service-role RPCs accept p_owner_id and must not be callable from an untrusted identity | O3, O6, O8 |
| Replay accepted, expired or revoked session; use suspended account | No private read, submission, signed delivery or privileged action | Fresh Auth user/claims, session liveness and admission are separate checks; verify every route, not just UI redirects | A1–A3 |
| Promote member to admin with forged role/AAL1 or stale admin status | No admin account updates, invitations, health or settings | Role read-back and AAL2 guard exist; adverse/step-up fixtures required for all admin handlers | A4–A5 |
| Spoof cron/reconciler credential, callback or provider handle | No global processing or unauthorized job mutation | Internal handlers use dedicated bearer checks; no browser identity should substitute for secret | I1–I2 |
| Cross-owner upload completion or collection membership | No signed R2 URL, file overwrite, foreign association, record deletion or cleanup | Upload sessions and associations are owner keyed; service role insert/upsert and idempotent paths require negative assertions | O4–O6 |
| Expose privileged DB error content in JSON, logs, stored metadata or alerts | No table/SQL detail, owner identity, storage key or token from upstream failure | **Known open P0-03 gap:** service-role REST wrapper includes up to 500 chars of raw upstream response; several route handlers return error.message and upload failures persist signingError | E1–E3 |
| Direct browser-role read of a server-only table or RPC | No read/write through anon or user JWT without explicit intended grant | RLS and grants are a distinct boundary from server service-role owner predicates; verify with read-only SQL/grant fixtures later | R1 |

No observed breach is asserted by this threat inventory. It identifies testable isolation and disclosure risks in the current implementation.

| /api/preview-account/* | Development/hosted relay only | Preserve destination authentication; no bypass via preview proxy | Unconfigured relay, forged owner header and production access (I3) |

**Account write policy (R12):** A suspended RenderLab account must not change display name, avatar image, or Create preferences. PATCH profile, POST/DELETE avatar and PUT/DELETE preferences require account access with `status === "active"`, in addition to fresh Auth and the existing route-specific MFA check. Suspension does not revoke recovery-oriented reads or other independently defined account security/recovery flows. Denial must occur before any profile, storage or preference mutation. This rule is separate from the generation/media member-access policy.

**Historical Unit 3 contract versus current implementation (R4, 2026-11-23):** this matrix began as a proposed threat-model inventory and is **not a blanket audit pass**. At the original checkpoint, [generation submit](../../src/app/api/generation/jobs/route.ts) used identity-only authorization while [job read](../../src/app/api/generation/jobs/%5BjobId%5D/route.ts) enforced active admission. [R4 PR #604](https://github.com/faresmohamed260/renderlab/pull/604) subsequently **merged** the correction: generation submit, cancel, retry and run-again now all invoke the canonical active-account/MFA gate; the public capability `GET /api/generation/jobs` remains exempt. [Route registry and adversarial tests](../../tests/unit/r4-member-route-registry.test.mjs) guard against reintroducing identity-only member access and exercise AAL1-enrolled, suspended and revoked denials. Merged code is **not evidence of a production deployment**. [Admin route authorizer](../../src/app/api/admin/admin-api-authorization.ts) and [same-origin mutation guard](../../src/server/security/same-origin-mutation.ts) remain separate controls, not substitutes for owner-scoped service-role queries.

## Mandatory service-role owner-filter inventory and test obligations

Every privileged `supabaseRest` **SELECT, PATCH, DELETE, INSERT/UPSERT and owner-taking RPC** in `src/server` must appear in a machine-readable **call-site registry**. A **static-scan registry test** enumerates call sites and fails on any unregistered, moved, removed, or newly introduced privileged call; each entry records the source location, table/RPC, principal derivation, and classification **`owner-scoped`, `admin`, `internal`, or `public`**. Classification is explicit and reviewable: a `public` exception is not implied by lack of an owner predicate; admin/global and internal sites need their corresponding role/AAL2 or bearer-secret gate. **Owner-scoped sites are exercised by data-driven negative harnesses per data family**, using two synthetic owners with foreign IDs and asserting the observed query/RPC/body contains the actor-derived owner filter. This avoids hundreds of hand-written tests while making every call site accountable to the scan and to a family harness. Registration without the corresponding family assertion does not satisfy the gate.

| Data families / inspected source | Required isolation assertion | Required case IDs |
| --- | --- | --- |
| [Access](../../src/server/account/account-access.ts), [profile](../../src/server/account/account-profile.ts), [preferences](../../src/server/account/account-preferences.ts) | user_id/owner_id must equal acting verified user; invitation claim never adopts unrelated user | O7, A1 |
| [Generation jobs](../../src/server/generation/native-generation.ts), [activity](../../src/server/generation/generation-activity.ts), [reconciliation](../../src/server/generation/reconcile-generation.ts), [claims](../../src/server/generation/generation-reconciliation-claim.ts) | owner_id combined with job ID; p_owner_id and provider handles cannot change a foreign job or settle foreign media | O1, O3, O8 |
| [Generation admission](../../src/server/generation/generation-admission.ts), [submit](../../src/server/generation/submit-generation.ts), [cancel](../../src/server/generation/cancel-generation.ts) | foreign reservation/job/source IDs denied on read, bind and release, without burning owner's slot | O3, O8 |
| [Media assets](../../src/server/media/media-assets.ts), [collections](../../src/server/media/media-collections.ts) | owner_id filter on each read/update/delete; insert and collection membership tie every asset to authenticated owner | O2, O4, O5 |
| [Uploads](../../src/server/media/media-uploads.ts), [references](../../src/server/media/reference-uploads.ts), [upload admission](../../src/server/media/upload-admission.ts) | owner-scoped session/source and upload RPC; signed delivery and cleanup occur only after correct ownership check | O3, O6 |
| [Account lifecycle](../../src/server/account/account-data-lifecycle.ts), session and profile services | exports/deletion/storage sweep for acting owner only; privileged background lifecycle targets documented server-selected owner | O7, O8 |
| [Admin operations](../../src/server/admin/admin-operations.ts), [admin settings](../../src/server/admin/admin-settings.ts) | global query/action permitted only after fresh admin AAL2; actor and target tracked separately | A4, A5 |
| [Diagnostics](../../src/server/observability/diagnostic-store.ts), [oldest job](../../src/server/observability/oldest-active-job-store.ts), [alerts](../../src/server/observability/operational-alert-notification.ts), maintenance | aggregate/global operator access requires admin or dedicated internal secret, output sanitized | I1, I2, E2 |

**Test technique (future 3b only):** use two synthetic admitted owners (A/B), a suspended owner, an active admin at AAL1/AAL2, an anonymous caller and revoked-session fixture. The registry scan must enumerate every `supabaseRest` call site and reject missing entries or mismatched principal classifications. For each owner-scoped family, run a table-driven harness with B's valid UUID/key on A's request, inspect the actual query/RPC/write body for the A-derived owner filter alongside the foreign resource ID, and assert zero B reads/writes and no external signed URL. For privileged global RPCs, test AAL2 or dedicated-secret authorization *before* the call. For SQL grants, separately verify anon/user JWT cannot impersonate service_role. No real accounts, production mutations or provider calls.

## Sanitized privileged-database failure contract (not yet implemented)

- Current [supabaseRest](../../src/server/data/supabase-rest.ts) includes up to 500 characters of an upstream error body in a thrown Error; [generation job GET](../../src/app/api/generation/jobs/%5BjobId%5D/route.ts), [media asset route](../../src/app/api/media/assets/%5BassetId%5D/route.ts) and [download](../../src/app/api/media/assets/%5BassetId%5D/download/route.ts) can forward error.message to clients. [Upload signing metadata](../../src/server/media/media-uploads.ts) can persist signingError from an exception. **These are confirmed code paths needing remediation and negative tests; no claim of actual secret exposure.**
- Required behavior: a stable domain error code and generic message to the client, with bounded internal status/correlation metadata. No raw SQL, response body, credential, path, user email, owner ID or storage key in response, log, diagnostic event, persisted upload metadata or alert. Preserve recognized safe typed domain errors; do not blanket-catch programming bugs as successful responses.
- Future E1/E2/E3 offline tests inject unique fake sentinel strings (SQL_DETAIL_SENTINEL, PRIVILEGED_TOKEN_SENTINEL and OWNER_B_SENTINEL) into fake PostgREST errors and storage/signing failures. Assert the strings never reach HTTP JSON, headers, server logs, persisted metadata or notifications. Assert response status/error code remains actionable and the server-only trace never contains secrets.
