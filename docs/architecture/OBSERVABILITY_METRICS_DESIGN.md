# FIBO generation observability — low-cardinality metrics and trace design

**Status: proposed, not implemented.** 2026-11-23. Design for today's invite-only FIBO image lifecycle, not shipped behavior or a Phase 3 score change. No runtime instrumentation, database migration, worker/Modal, secret, paid plan, notification, scheduler, generation or production release is authorized by this document. See [backend map](BACKEND_ARCHITECTURE_OVERVIEW.md), [state machine](P0_04_GENERATION_STATE_MACHINE_SPEC.md), [P0-06 limitations](../audits/P0_06_STATUS_CAS_FIX_RELEASE_PLAN_2026-11-23.md), and [incident runbook](../operations/INCIDENT_RESPONSE_AND_RECOVERY.md).

## Existing truth and gap

- [Typed diagnostics](../../src/server/observability/diagnostics.ts) already produce bounded structured console events and best-effort persistent events. [Diagnostic store](../../src/server/observability/diagnostic-store.ts) has application-managed 30-day retention and operational alerts. It recognizes gateway authentication rejection **only** for provider-poll HTTP 401/403, exposed in Admin Health as `gateway_auth_rejected`. Preserve that scoped rule; client 401 is not provider 401.
- [Admin Health](../../src/server/admin/admin-operations.ts) already reads active jobs, active unexpired reservations, [oldest active job](../../src/server/observability/oldest-active-job-store.ts), [outbox dispatch health](../../src/server/observability/dispatch-health.ts), bounded diagnostics and existing alerts. Oldest-active warning is **60 minutes**; outbox due-age threshold is **180 seconds**. These are distinct existing signals, not new Prometheus metrics.
- [Owner-return settlement](../../src/server/generation/owner-generation-settlement.ts) is triggered by Create, Activity, Library and blocked submit with bounded 1.5s lookup, 4s provider and 6s response-wait limits. An absent owner's finished provider result is **not automatically observable** without a separately approved callback/poll. [Native finalization](../../src/server/generation/native-generation.ts) and [admission release](../../src/server/generation/generation-admission.ts) are separate DB mutations.

## Metric catalog (proposal: nine series families)

Names are **logical application instruments**, not a claim that a Prometheus endpoint, stored histogram or alert exists. Fixed histogram buckets in **seconds**: `0.25, 0.5, 1, 2, 5, 10, 30, 60, 120, 300, 900, 3600, +Inf`. Proposed thresholds are **operator starting points, not approved SLAs or production-alert rules**. For percentiles and rates require at least 10 qualifying samples in the prior 15 minutes; no traffic means **no data**, not zero failures.

| Name / kind | Only allowed bounded labels | Emission point / measurement | Operator read path | Proposed alert |
| --- | --- | --- | --- | --- |
| `renderlab_generation_active_age_seconds` gauge, max | `status=queued/running/cancelling/persisting` | Read-only oldest per immutable `generation_jobs.created_at` in Admin Health, not `updated_at`; one gauge per state | Existing Admin Health oldest-active state/age; Vercel diagnostic log | 60m per-state warning **already exists**; do not confuse queued job age with separate outbox due-age >180s |
| `renderlab_generation_submit_duration_seconds` histogram | `operation=create-image` or reviewed enum; `outcome=accepted/rejected/timeout/error` | At POST `/api/generation/jobs` around validate→admit→durable enqueue; record status 202 only after accepted; `finally` on caught errors | Vercel Runtime Logs, proposed bounded `generation.submission` duration diagnostic in Admin Health | p95 >5s (n>=10), or repeated timeouts; investigate a single >8s on a deployment whose function timeout is 10s |
| `renderlab_generation_dispatch_latency_seconds` histogram | `backend=fibo`; `outcome=accepted/deferred/unknown/failed` | Durable accepted-job time→**confirmed** dispatch acknowledgement at outbox worker; ambiguous sends remain `unknown`, excluded from confirmed latency | Admin Health existing dispatch-health and new per-phase sanitized log | p95 >60s (n>=10); high if outbox due age >180s or unresolved >0 for 3m |
| `renderlab_generation_provider_rejections_total` counter | `operation` fixed; `category=auth/capacity/timeout/transport/other`; `status_class=4xx/5xx/none` | Signed provider submit/poll response; count once per **attempt**, not on every repeated poll, and preserve the existing 401/403 auth-gate semantics | Admin Health diagnostics code `gateway_auth_rejected` / provider-degradation alert, Vercel logs | **Immediate** investigation of first verified 401/403 from configured gateway; warn >=3 distinct errors/15m or >=10% with n>=10 |
| `renderlab_generation_provider_duration_seconds` histogram | `outcome=ready/failed/timed_out/unknown` | Confirmed provider acceptance→first **observed** ready/failed poll, not claim of exact GPU execution elapsed; omit if no trustworthy anchor | Existing provider-outcome diagnostics; propose bounded Admin Health derivation | p95 >240s n>=10 after baseline calibration; 2h provider-stale policy is separate |
| `renderlab_generation_finalization_duration_seconds` histogram | `outcome=succeeded/failed/cas_lost` | Successful status-CAS→`persisting`, then R2/index→terminal; only report `succeeded` after durable media index exists; CAS loser must not run side effects | Existing `provider-ready` / `finalization-complete` log phases | p95 >30s n>=10; investigate persisting >120s after known provider-ready |
| `renderlab_generation_admission_release_total` counter | `outcome=released/already_released/failed`; `path=terminal/replay/cancellation/expiry` | Record **result** of existing bound release/SQL RPC, not the attempted call; benign replay is separate from errors | Proposed result diagnostic, existing Admin Health active-reservation count | High any release failure after a terminal job; repeated failures >=2/15m |
| `renderlab_generation_terminal_held_reservations` gauge, sum | `terminal_status=succeeded/failed/cancelled` | Read-only aggregate join of terminal jobs with bound reservations `released_at IS NULL`; show **unexpired held** and separately note **expired unreleased** (not as owner ID series) | Operator-only Admin Health projection / bounded read-only SQL | High any unexpired held terminal reservation lasting >5m; investigate expired unreleased state, too |
| `renderlab_generation_provider_to_settle_seconds` histogram | `operation` fixed; `result=settled/recovered/unknown` | Only compare trustworthy provider-reported finish or **first observed** ready timestamp with `generation_jobs.completed_at`; record timing provenance privately, never fabricate actual provider finish | Correlated, restricted Vercel diagnostics; Admin Health oldest active where completion never observed | Warn observed ready→terminal >120s (n>=10); high known-ready-but-active >5m. With no owner return or provider callback, true provider-finished time is **unknown** |

**Cardinality/privacy contract:** never label by owner/user/job ID, provider call/worker handle, prompt/VGL, file name, R2 key, image URL, request ID, trace ID, raw error message, IP, user agent or unconstrained route/model string. The `operation` and `outcome` enumerations are strict allowlists, not free text. Limit diagnostic write volume and aggregate denominators; counters/histograms must not double-count reconciliation retries. A read-only snapshot may use privileged rows internally but exports **aggregate counts only**. Never put labels or trace data in public capability responses. All sampled logs are redacted and fail-open to application correctness.

## Logical trace model: submit → dispatch → provider → finalize → settle

Proposed private spans:
1. `generation.submit`: server-created W3C `traceparent`, 128-bit trace ID / 64-bit span ID, bounded flags. Inbound browser-supplied trace context is untrusted; validate syntax and generally start a **new server root** with optional link, never let it authorize owner scope or replay.
2. `generation.dispatch`: new execution on Next.js `after()` or background outbox delivery, **not** a parent that remains open after the submit response. Resume only if an approved durable, securely stored context exists; no such schema addition is authorized here. Otherwise link with RenderLab's existing restricted `correlationIdForGenerationJob(jobId)`, never as a metric label.
3. `generation.provider.submit` and `generation.provider.poll`: span around **server-only** authenticated Modal gateway calls. Propagate W3C headers **only if** the trusted gateway explicitly supports them without logging auth or changing signature behavior. Until then use a local boundary span, not a fake cross-provider trace.
4. `generation.persist` and `generation.media.index`: span actual R2 and Supabase operations after status-CAS; label outcomes as `succeeded` or `cas_lost` without claiming one physical R2 PUT or SQL transaction.
5. `generation.reconcile` and `generation.admission.release`: fresh span on owner return; link to prior phases by restricted internal correlation, and only record `generation.settled` after authoritative terminal status and released bound admission. A multi-day job **must not** be modeled as one continuously active HTTP span.

Structured private event sketch (proposal): `{event:"generation.reconciliation", phase:"provider-outcome", traceId:"<validated 32-hex>", spanId:"<validated 16-hex>", correlationId:"<bounded private join key>", operation:"create-image", outcome:"timeout", durationMs:4000, timestamp:"<UTC ISO>"}`. Existing diagnostics already have bounded event/phase/status/code and job correlation, but do **not** yet implement this full span convention. Trace correlation IDs are per-event internal join keys; not exported via public endpoints. Enforce schema allowlists, clamp numbers, exclude prompts, auth headers, raw provider responses and object keys. Sample **100%** of errors, release failures and terminal anomalies; optionally **10%** of ordinary success spans. Aggregate counters/gauges are never sampled. Telemetry errors must never reject a generation or mutate reservation state.

## Feasibility without new paid services

**Available now:** Existing Admin Health oldest-active, dispatch health, bounded recent events, 30-day application diagnostic table and operational alerts. Operator reads Vercel Function Runtime Logs (Hobby roughly **1h**, **4,000 rows**), Supabase Logs Explorer (Free API/database platform-log retention about **1 day**, subject to usage limits) and existing indexed Postgres rows. Application diagnostic table retention is **not** Supabase platform-log retention.

**Possible in a separately approved app-only implementation:** emit fixed JSON events into existing Vercel logs and bounded current diagnostic fields; add owner-independent aggregate projections to existing Admin Health with bounded queries. This is **not** a hosted metrics timeseries database: histograms/percentiles over short windows can be derived from bounded rows only when enough data exists; never promise 30-day accurate p95 from sampled logs. No extra service/credential/SQL table is necessary for a minimal first pass; a further database change requires separate approval.

**Optional, not assumed active:** Vercel announced native Tracing GA on **2026-11-06**, with **3-day Hobby trace retention**. Automatic enablement is conditioned on newer Next.js versions/new project rules; inspect the **existing** RenderLab deployment and its actual tracing setting before treating Vercel native traces as available. No automatic OTLP trace export should be inferred.

**Defer:** paid/unsupported Hobby log drains, full Prometheus/OTLP collector, high-volume traces, proprietary APM, paid Supabase Metrics endpoint, long-term centralized time series, new database aggregation tables, Modal/provider instrumentation, scheduled provider-poll finalization or alert-email changes. Supabase Logs Query consumption is usage-scanned: use short ad hoc dashboard filters, **not scripted polling**. Check current provider limits and rate/billing terms before any future implementation.

Vendor references, checked 2026-11-23: [Vercel Hobby](https://vercel.com/docs/plans/hobby), [Vercel Tracing GA](https://vercel.com/changelog/vercel-tracing-is-now-generally-available), [Supabase Logs](https://supabase.com/docs/guides/observability/logs), [Supabase pricing](https://supabase.com/pricing), [Supabase Logs Query usage](https://supabase.com/docs/guides/platform/manage-your-usage/logs-query). These are public limits, not a claim about the account's current billing plan or enabled features.

## How the three actual incidents would surface

| Incident | Proposed signal and operator action | What cannot be inferred |
| --- | --- | --- |
| **Gateway HTTP 401/403 outage** | Immediate `provider_rejections_total{category="auth"}` alarm, compare existing Admin Health `gateway_auth_rejected` provider poll diagnostics; check gateway/project credential wiring **without printing tokens**, avoid resubmission of ambiguous accepted jobs | A browser 401 or invalid user request does **not** count; provider 401 must be verified from signed gateway response |
| **Provider completed, job stuck running after tab close** | Active-age gauge warns at 60m even without a return; if provider-ready was **observed**, provider→settle delay >5m detects the missed finalization; check owner-return reconciliation | Without a provider callback or scheduled poll, the service **cannot know** that an absent owner's GPU job finished; no design-only metric repairs that |
| **Submit timeout / apparent locked slot** | Submit-duration histogram catches elapsed/timeout when response path executes; correlate a job's durable accepted state with admission-release counter and terminal-held gauge before deciding next action | A hard function kill may produce **no final diagnostic**, and a timed-out POST may already have been accepted. Never blindly retry an ambiguous submission |
