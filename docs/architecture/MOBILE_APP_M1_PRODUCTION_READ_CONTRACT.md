# Android M1 — existing production backend read-only contract (review candidate)

**Status:** Draft implementation-boundary proposal only. **Not M1 accepted, not merged, not authenticated, not installed, not released.**

## Owner-corrected goal (2026-10-27)

The installed native Instagram-style RenderLab client must read/write **RenderLab's existing production backend**, with live Metro/Fast Refresh iteration for user-directed text/icon/tab changes. The Expo SDK 53 third-party clone debug APK from PR #401 uses **only synthetic offline fixtures**. Its development-server chooser means Metro is not connected. It is not a production client and must not be given real RenderLab credentials. No second backend or Firebase integration.

The current verified production origin is `https://renderlab.faresuniform.uk`, from `docs/production/current.json`; deployment state is separate from this proposal. All application data remains server-owned through Next.js product APIs and Supabase Auth; no direct database, R2 or worker calls from Android.

## Actual server contracts inspected

| First M1 read | Existing route | Behavior |
| --- | --- | --- |
| Library items | `GET /api/media/assets?origin=generated\|uploaded&kind=image\|video&limit=24&offset=0` | `getCurrentRenderLabAccount()`, 401 without valid identity/MFA/admission, returns `{ok:true,items,page}` for owner |
| Collections | `GET /api/media/collections` | Same account gate and owner scoping, returns `{ok:true,collections}` |
| Profile | `GET /api/account/profile` | Profile owner gate, returns `{ok:true,profile,policy}` |
| Job status | `GET /api/generation/jobs/[jobId]` | Same owner gate plus opaque UUID and server-owned generation lifecycle (not in initial API wrapper) |

Server authentication already reads `Authorization: Bearer <Supabase user session token>` in `src/lib/supabase/server.ts`, then verifies the user, live claims/session, TOTP/MFA assurance and active invitation/admission. Do **not** bypass MFA or store a production token in a repository, APK constant, Metro bundle, logs, screenshot, test fixture, or chat.

## Implemented in this draft branch (no live credentials)

- `apps/mobile/src/services/api/production-read.ts` has an exact first-party production origin, typed source/media-kind/pagination options, strict fixed API endpoints and an **injected** native transport contract. No default React Native `fetch`, Auth client, file persistence or real HTTP requests exist. It requires a nonblank token **supplied by a separately approved session layer** and rejects redirect/foreign result metadata without fallback to fake fixtures.
- `apps/mobile/tests/production-read.test.mjs` covers endpoint selection, source filters, token requirement, unexpected CDN redirects, 401 and invalid responses using synthetic opaque tokens only.
- This M1 draft is **based on PR #399's SDK 58 M0 source**, not the vulnerable SDK 53 clone. That preserves the existing safe foundation and lets clone visuals be adapted selectively, not a blanket old-dependency adoption.

## Checkpoint 31 — controlled in-app presentation updates from the existing backend (draft, 2026-10-27)

**Owner direction:** use existing `renderlab.faresuniform.uk`, no WANDA, Codespaces, paid always-on Metro host, or second backend. Installed Android UI changes to copy, predefined icon variants and placement of **existing** tabs should take effect without rebuilding/installing an APK. No claim of unlimited code hot-reload or a fully production-ready binary.

**Draft implementation:** stacked PR #403 (`feature/android-live-ui-config-20261027`) adds a non-authenticated **GET `/api/mobile/ui-config`** to the RenderLab Next.js app, with fixed versioned JSON schema and a server-only `RENDERLAB_ANDROID_UI_CONFIG_JSON` override. The schema only permits:
- `brand`: bounded, plain non-control text (up to 24 chars)
- `tabs`: exactly the four existing Expo Router paths `index`, `library`, `activity`, `settings` **once each**, in a reorderable array; each has a bounded user-visible label (up to 18 chars) and one of three role-approved Ionicons
- `version:1` and a bounded `revision`, for client validation/change detection

Both web and native parse this schema **independently** (per the accepted mobile separation). Unknown keys, remote URLs, arbitrary components/JS, auth changes, new/deleted destinations, identity and role changes, invalid icons and control characters fail closed. The server returns `503` for malformed overrides without printing the value; the mobile app keeps its last accepted/embedded config on errors. Neither component sends or stores credentials; the endpoint never serves private media. The existing production Library/Auth contracts are unaffected.

The app's `RuntimeUiConfigProvider` refetches no-credential HTTPS JSON every **45 seconds while foregrounded**, and on return to foreground; layout labels, icon choices, tab order and RenderLab wordmark are React state. No Metro, remote code execution, APK reinstall, EAS account, OTA signing or device credential is necessary for **these specific presentational changes once a compatible APK and the route are deployed**. Standard native navigation, keyboard/accessibility destinations and underlying route implementations cannot be replaced via JSON.

**Operational limitation:** the checked-in default and optional server-only Vercel environment override are **deployment-time release inputs**, not an admin-facing live settings database. Changing those values requires a separately authorized backend deployment/release. This can update the installed app's UI without replacing the APK, but it does **not** satisfy instant editing without a server release. Persistent, mutable configuration via existing R2/DB would introduce a shared-resource mutation/security lifecycle and is **not implemented or approved**. Unauthorised users cannot change the public route; publication follows Git/operational approvals.

**Full JavaScript/asset OTA is distinct:** Expo SDK 58 supports `expo-updates` with either EAS Update or a fully compliant custom update server. EAS Update offers a limited Free plan, but requires Expo project/account linkage, update channel, native package ID, versioned runtime, code-signing policy, build/install and release controls. Neither EAS nor an unaudited self-hosted update protocol was silently provisioned. Native modules, manifest/permission changes and incompatible runtime require a new APK. The current Expo/node-forge dependency audit stays fail-closed; no live user Auth/MFA or production APK qualification is implied.

Unit Coverage, Engineering Quality, Documentation Governance, Developer Portability, CodeQL, UI Shell Validation and Brand/Launch Visual passed. No production hostname `/api/mobile/ui-config` deployment, native APK installation or device refresh was attempted.

**Next gates:** review the passing API/native checks, audit runtime label/icon changes on a real device and guest no-credential transport; review Android UI semantics and platform accessibility; obtain normal Security/Engineering/Owner release approvals for any server-side deployment, app signing or OTA activation.
