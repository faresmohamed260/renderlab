## 2. Cost model and invariants shared by all options

At observed warm A10 time, N=1/2/3/4 corresponds to approximately 33–35 / 66–70 / 99–105 / 132–140 renderer-seconds, before cold starts, VGL, failures, queue, transfer and any retries. Sequential completion latency is additive; parallel execution may improve wall time, not aggregate GPU seconds. Four existing 420 s execution ceilings would allow up to 1,680 invocation-seconds before overhead; neither 140 s nor 1,680 s is a verified billing cap. Actual billed container residency (including cold/warm idle, cancellation and rounding) requires authorized measurement. Modal timeout bounds execution, not invoice. No price or spending authority inferred.

Require owner-selected hard per-request budget B (aggregate permitted GPU execution seconds), per-slot max T, total rolling-hour image units and per-owner active group/concurrency limits, and a global capacity/kill switch. For launch, propose at most 4 slots and one active group OR ordinary single job per owner (honor tighter configured limits), one executing child per group, no parallel fan-out, reserve N image units at acceptance against the existing hourly policy (default 12; not 12 groups). Never refund an accepted unit simply because a user cancels; owner decides policy before implementation. Preserve distinction between hourly grants, outstanding reserved future slots, active execution and actual consumption. All paths (Create, Retry, Run Again, direct API) share the same owner lock and limits. Proposed policy must not count both a parent's reserved unit and a child grant or allow a legacy single job to bypass group occupancy.

Before each child starts, reserve its full remaining timeout envelope against B atomically; refuse another start if the remaining budget cannot cover it. Conservative charge for unknown execution until proved never started; no automatic refund/retry of ambiguous calls. Choose timeout plus overhead headroom from measured cold/warm behavior, not a hardcoded 35 s. Without a provider-confirmed hard billing limiter and attributable usage, expose only an execution-time bound, not dollar guarantees. If there is no safe B/T pair or provider quota/monitoring, remain disabled. Retries of transport/attach do not create new render entitlement. Each slot can be admitted to actual execution at most once via stable identity, but do not claim exactly-once external delivery. Reconciliation, cleanup and stop controls remain available even when new generation disabled.

## 3. Architecture options

### A — N independent jobs grouped by a group ID

- Admission: transactionally reserve all N units and group membership before any dispatch; sequentially admitting via independent public POST calls risks partial admission and key ambiguity. Launching N ordinary jobs simultaneously violates default active=1; even if limit raised, creates per-user/global concurrency and cost risks. Either reject N exceeding active cap or change scheduling and account policy. Aggregate time cap requires shared ledger and per-child timeout checks; a group ID alone is not enough.
- Failure/cancel: each job retains single-output lifecycle, succeeded assets survive failed siblings. Group Cancel must fence future sends and cancel running jobs individually, resolve races as truthful per-job outcomes; no all-or-nothing rollback. Group partial state derived from children, not arbitrary array length.
- Identity/persistence: owner+parent key maps to ordered child IDs; digest includes count and frozen seed/intent. Each child uses slot 0 and existing unique output identity; persist owner-scoped group/ordinal mapping, not client UUID arrays. Library/History group projection must not equate group and job IDs. No group-wide VGL guarantee if independent executions generate separately.
- Reconcile/deadlines: independent claims/cutoffs, group terminal when all children terminal; group budget/deadline and cancellation fence still needed. Unpolled recovery of multiple children must be bounded/fair. UI count 1–4, carousel and History driven by group projection; partially accepted subsets are forbidden. Add group metadata/unique owner membership, admission accounting and public projection. Tests: concurrent acceptance, no cross-owner mixing, stable child identities, partial failure, cancellation fan-out, legacy counts, expiry and reload. Easy per-job reuse but fragile if merely grouping N existing POSTs.

### B — one job with N output slots

- Admission: one reservation is insufficient without N weighted hourly and GPU units; one execution may loop sequentially through N graphs, preserving Studio-style VGL reuse/lock and avoiding repeated cold starts. Enforce aggregate B in worker before each graph and include renderer timeout/cancel margin. No GPU batching promised.
- Partial failure/cancel: requires a new legal terminal representation (or distinct outcome summary), because current job fails/cancels only with no indexed durable asset. Need per-slot state, independent durable commits while job is active, cancellation fence and explicit completed-but-cancelled batch semantics. Do not mutate successful slots or treat incomplete batches as full success.
- Identity/persistence: existing job+slot index is useful but insufficient; terminalizer accepts one asset, recovery/persistence hardcode zero, provider returns one PNG. Durable per-slot result transport and acknowledgement necessary before next graph; a single final response with N PNGs risks losing earlier results on interruption/size limit. Reconcile from rows and deterministic bytes per slot; generated VGL must be durable and validated before reuse. Idempotent acceptance includes N, resolved base seed and prompt; attempt/slot ledger prevents rerunning completed outputs after process death.
- Reconcile/deadline: redesign immutable deadline, lease/heartbeat, partial result retrieval, cancellation/persisting edges, provider payload/response and atomic release only at final group terminal. Old consumers assuming one output need compatibility/migration. UI count, carousel and group History map directly to a job, but require progressive status and per-slot asset projection. Tests: legal state-machine edges per slot, crash between R2/DB and graph boundaries, output index races, terminal partial asset guard, replays, group timeout/cancel. Broadest runtime/DB/gateway/contract rewrite; reject for first release.

### C — durable batch parent + serialized single-image child jobs (recommended)

A real orchestrator rather than a cosmetic group ID. Preserve existing single-image provider contract and per-job slot-0 terminalization; add a parent control plane with explicit future-slot intents and independent group status. Each parent has ordered N immutable slot intents; at most one child is materialized/dispatched at a time, and next only after previous child is durably terminal and group still eligible. Parent is not a renderer job and never submitted to the gateway. Do not implement as a browser loop or call ordinary POST N times.

**Admission/identity:** propose an additive server-only group acceptance RPC under owner/admission lock, atomically validate entire normalized intent, key digest incl count, seed mode and options; resolve random base seed exactly once, reserve all N rolling-hour units and group occupancy, create slot intents plus first child reservation/job/outbox, and return stable opaque group ID. Group key namespace must prevent a single-request key being reused as a changed group intent (shared namespace or explicit version discriminator); same owner/key/digest replay returns identical group/slots even after timeout, conflict on mismatch, no new grants. Resolve missing key according to current single-intent rules; UI explicit key survives uncertain response/reload. Each child has stable server-generated identity derived from group+ordinal or unique stored mapping, separate acceptance/attempt IDs; retry delivery attaches same attempt. Transactionally consume next reserved unit and create child/job/outbox with no additional hourly grant. Introduce compatibility-aware accounting so released child reservation does not open an active-limit gap while parent remains active. Lock ordering documented/tested across ordinary submit, group submit, cancel, advance, account delete; no network inside SQL locks.

**Scheduling/settlement:** durable controller claims group via bounded lease/CAS; never hold lock over provider IO. Child completion settles through existing claimed job path then advances via atomic parent transition (or atomic terminal-triggered advancement if reviewed); crash after child terminalization before advancement recoverable via scan. For unattended sequential progress need separately authorized bounded settlement/advance runner, restricted scope/privileges, owner fair scheduling, no new broad credentials; do not piggyback unbounded provider calls on existing dispatch cron or Next.js after(). Alternative owner-return-only mode is explicit UX downgrade (paused until return); do not ship claiming background progress with that mode. Bounded runner reuses existing reconciliation claims; no simultaneous competing provider polls. Persisting recovery prioritizes bytes/rows, then provider result, then existing deadline rules. Use stable per-child admitted timestamp/deadline no extension on replay; separate immutable parent hard deadline includes sequential queue, execution and persistence headroom. Before admission of next child require enough time for its full T and persistence margin; when parent cutoff arrives fence new children, cancel/reconcile current, settle unused slots, release occupancy only after known terminal or existing conservative recovery ceiling with unresolved attempt evidence retained. No false proof of stopped GPU or automatic replacement after unknown outcome. Never leave unresolved outbox or expired reservation to masquerade as healthy; monitor parent stuck, unknown sends, expired leases and budget exhaustion separately from existing outbox health.

**Failure/cancellation:** v0.1 stop on first non-success (no automatic rerender of a failed slot). Parent outcome is separate from child enum: queued/running/stopping, complete (all N succeeded), partial (at least one success and not all N), failed (zero success, failure), cancelled (zero success, explicit cancel); include sanitized stop reason and per-slot pending/running/succeeded/failed/cancelled/not-started state. Parent cancel first records durable stop fence, prevents new slots from being dispatched under same lock as advancement; if a child is accepted-but-not-started use existing queued cancel; if running use existing provider cancel; if persisting let existing persistence finish. Show stopping until child settles; a completion racing cancel remains a valid saved asset. If all N complete despite late cancel, report complete, not cancelled. Repeated cancel idempotent; terminal parent immutable except asset visibility (deletion). Already succeeded child jobs unchanged. No retry-partial or resume UI in first release; Run Again creates a fresh explicit request/entitlement, never reopens group. Account deletion fences admission/advance and reconciles active work before verified cleanup; existing tombstones and R2 cleanup remain per asset.

**VGL and seeds:** freeze base seed in server normalization, use owner's one-based modular formula with exact integer-safe arithmetic and verify deployed MAX_SEED bound from current parser/worker before implementation; reject unsupported range rather than silently truncate. Index zero uses base; test wrap at max, replay and randomization once. Freeze canonical prompt, dimensions/model/steps and conditioning. First-release scope propose source-free text-to-image using already-supported prompt modes (plain/manual VGL where supported); defer references/mask/inspiration, negative conditioning and generated-VGL exposure. If explicit manual VGL supplied, reuse validated identical instruction for each child. Studio first-generated-then-reuse optimization requires a separately approved server-generated VGL path: persist validated sidecar with version/hash/owner and first child terminal checkpoint, then later children consume exact validated instruction with their new seeds, not a browser-supplied rewrite. Missing/invalid sidecar stops group, never silently regenerates VGL or falls back to another model. Until that is separately qualified, do not promise Studio automatic VGL reuse or identical scene coherence; baseline repeats the already-supported ordinary prompt graph per child. If product requires automatic reuse at launch, keep feature disabled until that gate passes; do not turn on other disabled capability to meet schedule. Separate child calls may be slower/costlier than Studio in-process reuse; measure.

**Schema and privacy (proposal only):** new RLS-enabled browser-revoked generation_groups and generation_group_slots (owner/group ID, ordinal 0..N-1, requested count, immutable normalized intent/digest or reference, seed/seed mode, state/stop reason, reservation/usage ledger, deadline, lease, child job ID; unique group+ordinal, unique child association, owner-consistent FKs); use existing child media asset ownership and storage keys. Parent provenance never exposes provider/worker IDs, object keys, signed transport handles or raw diagnostics. Add owner-scoped group idempotency identity and indexes for bounded recovery; retain keys through published replay window, never delete unresolved evidence. Add export/delete/maintenance coverage, service-role-only RPCs with empty search_path, minimal restricted privileges for runner, same-origin verified account and existing admission/security checks. Existing jobs/media unchanged; legacy single jobs are singleton presentation with no inferred group, historical null-index extras remain noncanonical. Additive migrations only after approval; no backfill of groups from timestamps or similarity. Review actual migration numbers then. Group count/ledger consistency enforced transactionally, not by UI.

**Product contract (not current API):** additive versioned group submit/status/cancel endpoints or explicit opt-in envelope, leaving old single-job response shape and default 1 unchanged. Include group ID, requested count, ordered slot statuses, nullable active same-owner asset IDs, succeeded count, sanitized reason, cancel eligibility; no raw VGL sidecar by default. Server capability advertisement must gate count 2–4, reject malformed/disabled counts before admission. Existing count=1 path stays exact; don't silently coerce invalid values. On Create use maintained shared Input/selector, accessible carousel and ordered slots; first image appears immediately after durable persistence, next slot progress without blanking it; no premature success, no fake progress or spin for completed slots. Reconnect/reload from server group identity, dedupe by asset ID and ordinal (not filename), preserve current selection; accessible keyboard/focus/live announcements, reduced motion, narrow/200% zoom, error/cancel states, no new top-level Activity route or dependency on Activity UI (owner's design direction). Create History groups by group ID with count and partial indicator; Library keeps individual durable assets searchable/favoritable/deletable with optional group indicator and owner-scoped group drill-in; don't break asset-first pagination or collect foreign/deleted assets. Groups may straddle pages; fetch bounded members by group ID rather than deriving count from a page. Tombstone removes access, does not rewrite recorded historical success or allow resurrection. Reuse Settings reads selected child's persisted settings; future batch rerun explicit, not implicit on opening. Follow UI source policy and Phase 6 approved design review before implementation.

**Trade-off:** more control-plane schema/runner than A, but avoids B's changes to per-render provider payload, cancellation and slot-0 terminalizer. Requires deliberate admission accounting, runner availability and privacy/cleanup work; no claim implementation is trivial. If an unattended runner cannot be safely qualified, do not substitute a fragile browser loop. Evaluate B only if measured sequential child overhead makes C unacceptable and owner approves a wider lifecycle rewrite.
